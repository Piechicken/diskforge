# Changelog

All notable changes to DiskForge are documented in this file. The project uses semantic versioning for public releases.

## v0.10.0 — Verified Cross-Platform Disk-Image Workflows

DiskForge v0.10.0 is a formal release that consolidates verified image-content workflows while preserving the principle that a byte-stream extension or a boot catalog is never treated as permission to make an unsafe or ambiguous modification. It is a stable, format-specific release: supported write paths remain explicit, and unsupported historical encodings continue to be refused rather than guessed.

| Area | Additions in v0.10.0 |
|---|---|
| Rebuild-based ISO editing | ISO content can be rebuilt into a separately named output after explicit file/directory addition, deletion, and directory creation. Every staged file is SHA-256 verified; the source remains unchanged. Rock Ridge and UDF naming profiles are detected and preserved. |
| Controlled El Torito preservation | Safe reconstruction preserves a verified single initial El Torito entry, including the boot image, bootable state, platform ID, media type, load segment, system type, load-sector count, and boot-information-table choice. Boot image and generated catalog paths are protected from edits. Multi-section/multi-boot catalogs, hybrid system areas, and non-unique catalog mappings are rejected rather than rewritten. |
| ISO command and batch closure | `edit-iso` is available in the CLI. Batch schema v4 adds declarative `iso_edit`, with preview-before-write and the same core safety guards. The desktop ISO action now describes its actual safe scope rather than implying that only plain ISO media is accepted. |
| Legacy IMG/IMA creation | IMA is now a distinct first-class raw-image target, while retaining its flat-sector semantics. The desktop, CLI, batch conversion, and format selector support explicit IMG or IMA output. New verified FAT12 profiles cover conventional PC-compatible 5.25-inch and 3.5-inch 160 KB through 2.88 MB layouts, including DMF and 82-track layouts; custom supported CHS geometry is explicit. |
| Legacy image editing | A valid FAT IMA follows the same native workflow as a FAT IMG: browse, internal preview, inject, delete, rename, adjust standard attributes, extract, hash, and convert. The UI offers the full profile directory, IMG/IMA selection, custom geometry, and complete seven-language labels. |
| Controlled NTFS/EXT injection | Optional `ntfsprogs` and `e2fsprogs` adapters can add regular local files to a **new standalone output image**. The source remains SHA-256 unchanged; targets are root-only and must not exist; write-back is preflighted or undo-logged, read back, SHA-256 verified, and reopened/validated before promotion. Desktop, CLI, and batch v4 expose the same copy-on-write contract. |
| Controlled classic HFS injection | Optional `hfsutils` support adds root-level regular local files to a **new standalone classic HFS output** only. Each operation receives an isolated `HOME`; `hls` stderr is parsed for the required absence diagnostic before `hcopy -r`; every raw data fork is read back and SHA-256 verified; the source digest and HFS signature are rechecked before atomic promotion. Desktop, CLI `inject-hfs`/`hfs-inject-status`, batch v4 `hfs_inject`, the graphical designer, and all seven interface languages expose the same contract. HFS+ remains read-only. |
| Verified classic HFS creation | Optional `HfsImageCreator` creates a new standalone classic HFS regular-file image through explicitly available `hformat`. It accepts only a new file target of at least 800 KiB in 512-byte units and a constrained 1–27-character ASCII volume label; it rejects devices, existing targets, partition maps, partition ordinals, `-f`, MFS, and HFS+. Creation allocates a unique sibling temporary file, uses isolated `HOME`, verifies the HFS signature and output SHA-256, then atomically promotes the output. Desktop New Image, CLI `create-hfs`/`hfs-create-status`, batch v4 `hfs_create`, the graphical designer, and seven-language text all expose this exact optional contract. |
| Explicit read-only partition browsing | A validated, caller-selected MBR/GPT table index can now open FAT, NTFS, EXT, classic HFS, or HFS+ partitions through the same core route. FAT retains its established writable session; all non-FAT partitions are passed to the read-only adapter at their exact validated byte offset. Unknown partitions and every non-FAT write request are rejected before an external backend starts. Desktop, CLI, SDK, GUI action state, and tests use this one route. |
| Universal directory reports | Every browsable filesystem now shares a stable, cancellation-aware full traversal for text or HTML directory reports with escaped HTML paths. The report writes only a new local report file; it does not alter the source image. CLI `export-listing`, desktop export/print, and batch v4 `export_listing` can use an explicitly selected read-only partition. The graphical recipe designer and all seven UI languages cover the new operation. |
| FAT file and directory-tree movement | A regular file or complete directory tree may move into an existing directory within a writable FAT image without overwrite. Regular files use the filesystem primitive; directories use a cancellable, controlled copy-then-delete workflow that leaves the source intact until the new destination tree is complete. Core preflight rejects the root, missing/non-directory targets, target collisions, read-only sessions, and directory targets within the source tree. Directory movement is not claimed to be atomic: if source deletion fails, both complete trees are retained for manual resolution. CLI `move-fat`, SDK `DiskForgeClient.move_fat`, batch v4 `move`, the desktop action, graphical recipe designer, optional validated FAT partition routing, and all seven UI languages expose one consistent contract. |
| Explicit empty FAT directories | A writable FAT image or explicitly selected FAT partition can create one empty directory whose parent already exists. The core rejects the root, pre-existing paths, missing or file parents, read-only sessions, and cancellation before mutation. CLI `mkdir-fat`, SDK `DiskForgeClient.create_fat_directory`, batch v4 `fat_mkdir` with `will_write` preview, the graphical recipe designer, a seven-language desktop action, and partition-preserving worker routing share the same contract. |
| FAT file and directory-tree copying | A regular file or complete directory tree can be copied within a writable FAT image into an existing directory while retaining its source bytes. The same-name target must be new and, for a directory source, must not lie inside its source tree. The core streams file data with cancellation checks and removes the newly created target tree after failure where possible; it rejects the root, missing/non-directory targets, existing targets, read-only sessions, and unsafe source-tree targets. CLI `copy-fat`, SDK `DiskForgeClient.copy_fat`, batch v4 `fat_copy` with `will_write` preview, the graphical recipe designer, a seven-language desktop action, and partition-preserving worker routing share the same contract. |
| FAT entry renaming in all automation surfaces | Same-parent renaming of one FAT file or directory is now a first-class SDK method, `DiskForgeClient.rename_fat()`, and batch v4 `fat_rename` operation. Both require an explicit source item and a single non-empty new entry name, reject collisions and unsafe partition indices, and never overwrite an existing entry. The graphical recipe designer persists/reopens the source, item path, new name, and optional FAT partition; its labels, validation messages, and safety hint have complete seven-language coverage. |
| Explicit FAT deletion in all automation surfaces | One explicit non-root FAT file or directory tree can now be deleted through the strengthened core preflight, CLI `delete-fat`, `DiskForgeClient.delete_fat()`, and batch v4 `fat_delete` operation. Every request validates all targets before mutation, rejects the root, empty or duplicate requests, read-only sessions, and unsafe partition indices. The graphical recipe designer persists/reopens the path and optional partition and presents an irreversible-deletion warning in all seven languages. Directory-tree deletion is intentionally not claimed to be transactional. |
| Safe ZIP single-image browsing | A regular `.zip` may now open as a **read-only** image container when it contains exactly one safe, root-level, directly browsable image payload. The core streams that payload into an auto-cleaned private temporary session, re-identifies its filesystem, then routes CLI `list`/`extract`/`export-listing`, SDK filesystem/extraction, batch v4 read operations, and desktop browse/preview through the same read-only adapter. The ZIP source never changes. |
| Conservative FAT deleted-file candidates | FAT12/FAT16 fixed-root directories can now be scanned for ordinary 8.3 deleted-file candidates. A candidate is recoverable only when its start cluster is currently free and its declared payload fits one cluster; recovery copies only that candidate to a **new local output file**, never writes the image. CLI `list-deleted-fat`/`recover-deleted-fat`, SDK candidate/recovery methods, and a seven-language desktop workflow share the same revalidation and source-preserving contract. |
| Safe IMD inspection and RAW export | IMD floppy-sector containers can now be inspected read-only. A new RAW output is permitted only for a proven complete rectangular CHS layout with fixed sector geometry, consecutive sector numbering, no optional maps, and normal (including normal compressed-fill) data in every sector. CLI `imd-info`/`convert-imd`, SDK methods, and a seven-language desktop inspector share the same no-source-write, no-overwrite contract. |
| Read-only batch image inventory | A local directory can be scanned for recognized image candidates and filtered by suffix, recognized format, filesystem, byte range, or SHA-256 prefix. The core can emit atomic new JSON, CSV, or HTML reports; CLI `inventory-images`, SDK inventory/export methods, and a seven-language desktop tool expose the same source-preserving workflow. Optional per-record SHA-256 and partition summaries are explicit. |
| Restricted TD0 inspection and RAW export | Ordinary uncompressed TD0 floppy-sector containers can now be structurally inspected read-only with header, comment, track, sector-flag, and encoding checks. A new RAW output is permitted only for a CRC-validated, exact-EOF, unflagged complete rectangular CHS layout with fixed geometry, matching logical/physical coordinates, consecutive sector IDs, and exactly reconstructed ordinary data. CLI `td0-info`/`convert-td0`, SDK methods, inventory recognition, and a seven-language desktop inspector share the same no-source-write, no-overwrite contract. |
| Explicit FAT metadata batches | Existing writable FAT entries can now receive explicit standard DOS attribute and/or FAT creation, modification, and access-time updates in caller order. CLI `set-fat-metadata`, SDK `DiskForgeClient.set_fat_metadata()`, batch v4 `fat_metadata`, the graphical recipe designer, and a seven-language multi-selection desktop workflow share one validation and cancellation-aware core. Batch preview labels the operation as a write before execution. |
| Restricted CPC DSK inspection and RAW export | Signed standard and extended CPC DSK containers can now be structurally inspected read-only. A new RAW output is permitted only for an exact-EOF complete physical cylinder/side layout with matching track and sector coordinates, clean controller status, fixed sector geometry, consecutive IDs, and exact single-copy sector data. CLI `cpc-dsk-info`/`convert-cpc-dsk`, SDK methods, inventory recognition, and a seven-language desktop inspector share the same no-source-write, no-overwrite contract. |
| Restricted D88 inspection and RAW export | Shape-validated single-disk D88 containers can now be inspected read-only. A new RAW output is permitted only for an exact-size first disk with a valid track-offset table and complete clean rectangular sector geometry. CLI `d88-info`/`convert-d88`, SDK methods, inventory recognition, and a seven-language desktop inspector share the same no-source-write, no-overwrite contract. |
| HFE structural inspection | HFE v1/v2/v3 bitstream containers now receive a read-only header, LUT, track-range, and side-interleave structural check through `hfe-info`, the SDK, inventory recognition, and a seven-language desktop inspector. HFE bitstreams are not decoded, flattened, edited, or opened as filesystems. |
| DC42 inspection and data-fork RAW export | DiskCopy 4.2 containers are validated for the fixed header, exact forks, and data/tag checksums. `dc42-info` and `convert-dc42` export only a fully verified data fork to a separate new RAW file; tag data and source bytes remain untouched. |
| 2MG/2IMG inspection and data-block RAW export | Standard 2MG/2IMG containers are structurally checked for their header, format, flags, and contiguous optional blocks. `twoimg-info` and `convert-twoimg` can export only a verified DOS/ProDOS data block into a new RAW file; NIB images remain inspection-only. |
| APRIDISK inspection and strict RAW export | APRIDISK record streams now receive signature, record, and RLE validation. `apridisk-info` and `convert-apridisk` export only normal/RLE sectors that prove a complete non-deleted rectangular layout. |
| CopyQM inspection and strict RAW export | CopyQM headers, comments, symbol-length RLE, geometry, and masked checksums are inspected read-only. `copyqm-info` and `convert-copyqm` export only a complete checksum-verified fixed DOS geometry to a new RAW file. |
| SAP inspection and strict RAW export | Thomson SAP headers, data deobfuscation, Pukall CRC, protection state, and sector geometry are checked read-only. `sap-info` and `convert-sap` export only ordinary unprotected CRC-valid rectangular sectors to a new RAW file. |
| MSA inspection and strict RAW export | Atari ST MSA headers and every uncompressed or E5-RLE track are fully decoded before `msa-info`/`convert-msa` permit a separate RAW output. Invalid RLE, geometry, or trailing bytes are rejected. |
| PSI inspection and strict RAW export | PSI chunk CRCs, standard sector/data/fill records, and safe metadata are checked read-only. `psi-info` and `convert-psi` export only normal, complete rectangular sector layouts; weak, alternate, bad-CRC, irregular, or unsupported chunk paths are rejected. |

### Explicit boundaries

v0.10.0 does **not** claim editable support for every historical floppy encoding. A regular ZIP is not a generic image filesystem or conversion format: one to 64 root-level, unencrypted Stored/Deflated direct-image payloads no larger than 2 GiB may be materialized for browsing only after every member validates. A sole payload opens directly; multiple payloads require an exact explicit selected name. Folders, unsafe names, unknown methods, empty/oversized/unknown payloads, more than 64 entries, recursive containers, virtual-disk chains, and all ZIP writes are rejected. Temporary payloads are removed on close, error, or cancellation. FAT deleted-file recovery is not generic forensic recovery: it supports only FAT12/FAT16 fixed-root ordinary 8.3 slots with a positive single-cluster payload and a currently free start cluster; deleted names have a lost first character, output bytes may already be stale or overwritten, and no original-name or integrity claim is made. FAT32, subdirectories, long names, zero-length or multi-cluster chains, non-free clusters, source-image writes, existing-output overwrite, device recovery, and all automatic/batch recovery are rejected. FAT movement supports regular files and complete directory trees: it requires an existing target directory and new same-name target, never overwrites or merges entries, rejects the root and a target inside the source tree, and handles directories by controlled copy-then-delete. The source remains intact until copying completes; cancellation before deletion retains source and new destination, and a deletion failure likewise retains both trees for manual resolution. This is deliberately not claimed to be an atomic filesystem transaction. Same-directory renaming remains a distinct `rename` workflow. Empty FAT-directory creation is explicit and non-recursive: the requested path must be new, must not be the root, and its parent must already be an existing directory; it never overwrites a path or creates an implicit directory tree. FAT copying supports regular files and complete directory trees: it requires an existing target directory and a new same-name target, preserves the source, never overwrites or merges entries, rejects the root, and rejects a directory target that lies inside the source tree. A failed or cancelled operation makes a best-effort removal of the newly created target tree; it is not claimed to be a transactional filesystem operation.  Flat-sector FAT creation supports 512, 1024, 2048, and 4096-byte sectors. 128/256-byte-sector media, GCR or variable-sector encodings, hard-sectored disks, copy-protected tracks, non-FAT filesystems, and flux/bitcell captures remain raw-byte inspection, preservation, checksum, and comparison workflows unless and until a separately validated track-level backend exists. NTFS/EXT/classic-HFS injection is **optional external-backend support**, not native or universal writing: it rejects partition-offset and physical-device paths, pre-existing targets, directories, metadata/ACL/ADS work, delete/rename, and all in-place writes. Classic HFS transfers raw data forks only; no MacBinary, Finder metadata, or resource-fork reconstruction is claimed. HFS+ remains read-only; no journaled HFS+ write or filesystem repair is claimed. IMD support is inspection plus a narrowly proven new RAW export only: mapping records, irregular or incomplete CHS geometry, variable sector sizes/counts, nonconsecutive IDs, missing/deleted/bad sectors, trailing bytes, source writes, output overwrite, device targets, IMD writing, bitstream/flux analysis, and media-device operations are rejected. TD0 support is likewise an inspection plus narrowly proven new RAW export only: it accepts normal uncompressed `TD` records and rejects advanced-compressed `td`, multi-volume sequences, any CRC mismatch, trailing bytes, flags or missing data, mixed density, nonrectangular/variable geometry, logical/physical coordinate mismatch, nonconsecutive IDs, source writes, existing output, devices, TD0 writing, filesystem editing, repair, bitstream/flux analysis, and media-device operations. CPC DSK support is inspection plus a narrowly proven new RAW export only: signature identification is required because `.dsk` is ambiguous; unformatted tracks, controller status, coordinate mismatch, variable geometry, nonconsecutive or repeated IDs, short/long/multi-copy sector data, tail bytes, source writes, output overwrite, devices, DSK writing/editing/repair, filesystem browsing, copy-protection, weak-sector, bitstream, and flux claims are rejected. D88 support is inspection plus a narrowly proven new RAW export only: it accepts one exact-size disk with a validated 0x2A0/0x2B0 first-track offset and rejects multi-disk/trailing data, irregular offsets, unformatted or incomplete geometry, deleted/status-marked sectors, data-length anomalies, source writes, output overwrite, devices, D88 editing/repair, filesystem browsing, copy-protection, weak-sector, bitstream, and flux claims. FAT metadata batches are limited to explicit existing paths in a writable FAT image or an explicitly selected FAT partition. Only standard read-only, hidden, system, and archive bits and caller-supplied timezone-free FAT times are accepted; empty requests, root paths, duplicates, wildcards, recursion, implicit current timestamps, devices, non-FAT filesystems, ACL/ADS/ownership changes, forensic claims, and automatic selection are rejected. A batch validates before execution but FAT directory updates across multiple paths are not claimed to be an all-or-nothing transaction. Batch inventory is a read-only local-file report, not an unattended mutation or forensic scanner: it accepts only an existing non-symlink directory, ignores symbolic links, recognizes only known image suffixes, discovers at most 10,000 regular files, excludes files above 16 GiB, and can only write a new JSON/CSV/HTML report outside the scanned root. It does not follow links, mount images, inspect physical devices, overwrite reports, or enter batch schema v4.

### Additional v0.10 read-only container boundaries

### Optional integrations

NTFS and EXT2/EXT3 browsing require locally installed Sleuth Kit `fls` and `icat` executables. Virtual-disk conversion for VHDX, VMDK, and QCOW2 continues to require a locally configured `qemu-img` executable. DiskForge does not install, download, mount, or invoke external tools without an explicit user configuration or invocation.
